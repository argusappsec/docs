# ADR 0008 — Cloudflare Web Analytics, and the script the guard cannot see

**Status:** Accepted
**Date:** 2026-08-04

## Context

Nothing measures whether this site works. The Landing was iterated by eye over
several rounds, and there is no way to tell which of those rounds mattered.

The site's own rules make this awkward. ADR 0007 records that the Landing carries
**one** script, inline, and that a second has to argue for itself;
`src/landing/landing.test.ts` asserts that count, because every failure it guards
against is silent. Any analytics product is a second script.

Three candidates were weighed:

- **Umami, self-hosted.** A Next.js app plus a PostgreSQL database, so it needs a
  process that runs and a disk that persists. Cloudflare Pages hosts neither. The
  free paths all fail: Vercel Hobby is the clause ADR 0005 already rejected for
  the site, and it defines asking for donations as commercial use; Render's free
  service sleeps, so the first visit of a quiet day arrives while the container
  wakes and is lost; Fly.io no longer has a free tier. It is a small paid VPS or
  nothing, and a VPS is a second thing to keep patched — for a security tool's
  own website, that is a real cost and not a rounding error.
- **Umami Cloud.** Adds a processor and a transfer question, and its domains are
  on the common blocklists.
- **Cloudflare Web Analytics.** Free on any plan, cookieless, no database, no
  server.

Accuracy cuts against all three equally and is worth stating plainly: this
audience runs content blockers. `static.cloudflareinsights.com` is on the same
lists that carry Umami's domains, so every option here undercounts developers.
Umami on a subdomain of this site would be the least blocked, because that
hostname is on nobody's list. That is the one real argument for the VPS, and it
did not win.

## Decision

**Cloudflare Web Analytics, and a privacy notice at `/privacy/`.**

Cloudflare is already the CDN and the DNS for this domain, so it already sees
every request and the IP address behind it. Choosing its analytics introduces no
processor that was not already in the chain, which is why the privacy notice can
be as short as it is: one company, no cookies, no consent banner, and 7 days of
unsampled retention before Cloudflare aggregates it away.

The notice lives at `src/content/docs/privacy.md` — inside the docs collection so
it inherits the whole Starlight layout for free, and **outside the Mirror**, whose
blast radius ADR 0002 scopes to `src/content/docs/guide/`. The Sync deletes as
well as adds; a hand-written page one directory deeper would vanish on the next
run. It stays out of the sidebar because the sidebar is autogenerated from `guide`
only, and out of the Landing's footer reading list because `guideHandoff` filters
to the Mirror's ids.

ADR 0007 called `src/content/docs/` "otherwise the Mirror's home" when it turned
down a Starlight splash page at `/`, and this is the first page this repository
authors to live there. The two are consistent: what that phrasing was protecting
is the Sync's blast radius, and the Sync replaces one directory deeper. What it
was also protecting — that the Landing not be a Starlight page — is untouched.

## Consequences

- **The zero-JavaScript rule is now "one inline script, plus a beacon injected at
  the edge".** For a proxied zone Cloudflare's automatic setup is on by default
  and inserts `beacon.min.js` into the HTML response. The rule ADR 0007 states is
  therefore relaxed here, deliberately, and the relaxation is worth naming rather
  than discovering.

- **The Landing's script guard cannot see it, and would keep passing while the
  rule it protects is broken.** That is the whole reason this ADR exists. The
  guard reads `src/pages/index.astro`; an edge-injected script is in neither the
  source nor `dist/`. So the test still asserts exactly one inline script and
  remains correct about what this repository writes, and this document is the only
  record of what the served page actually ships. If the beacon is ever installed
  the other way — the manual JS snippet, pasted into the page — then the guard
  *does* see it, and the honest move is to widen the test to two scripts rather
  than to delete it.

- **A Content Security Policy would have to allow the beacon.** There is none
  today. Recorded because adding one later without the allowance would break the
  measurement silently, which is the failure mode this repository keeps writing
  tests about.

- **`privacy@argusappsec.com` exists**, added when this was written. The notice
  publishes it as the address to write to, and the domain's MX records point at
  iCloud Mail (ADR 0005), so a bounce here would take the page's one obligation
  with it. Kept separate from `security@argusappsec.com` on purpose: a
  vulnerability report and a subject access request should not queue behind each
  other.

- **Cloudflare offers "enable, excluding visitor data in the EU"**, which skips
  the beacon for European visitors and removes the GDPR question by removing the
  measurement. Not taken: this project's readers are mostly in Europe, and a
  notice is cheaper than blinding the instrument.

- **The measurement is thin by construction.** Pages, referrers, countries and
  Core Web Vitals, with no custom events and no funnels. If a question ever needs
  more than that, it needs a different product, and this decision gets revisited
  with the VPS argument above already written down.
